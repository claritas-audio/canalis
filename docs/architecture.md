# Architecture

## Two planes
```
                 channels                      spawns / supervises
 apps/canalis  ◄──────────►  canalis-pw   ─────────────────────────►  canalis-chain (×N)
 egui GUI                    pw main loop                              pw stream pair
                             registry mirror                           slots in callback
                             link/unlink/metadata
        ▲                          ▲                                        ▲
        └──────── PipeWire daemon + WirePlumber ────────────────────────────┘
```
- **Control plane (`canalis-pw`).** Runs the `pipewire` main loop on a dedicated thread (the loop is `!Send`). Mirrors the registry into `model::{Node, Port, Link}` snapshots sent to the GUI; receives `Command`s (link, unlink, create virtual device, set default, move stream). Creates links with the `link-factory` and `object.linger = true`; creates virtual devices by loading `libpipewire-module-loopback`/`support.null-audio-sink` nodes; writes WirePlumber metadata for defaults and `target.object`.
- **Audio plane (`canalis-chain`).** One process per chain, so a crashing plugin takes down one chain, not the desktop. A chain is a capture stream and a playback stream serviced in one process callback, as `module-filter-chain` does: the capture stream connects with `ASYNC` and only triggers the playback stream, whose callback dequeues the newest capture buffer, runs the slots in place on planar f32 and queues both buffers back. Each end is either published to apps as a virtual device or linked to nodes the user picks, which gives four chain types from one mechanism: *output* (capture side is `media.class = Audio/Sink`), *mic* (the playback end feeds a `support.null-audio-sink` of class `Audio/Source/Virtual` named after the chain, which the chain process creates and apps record from; PipeWire 1.6 gives a plain output stream of that class one input port and nothing to record), *cable* (both: apps play into it and record from it), *insert* (neither). The device end carries the chain's `node.name` (`canalis.<slug>`), the stream ends are `<name>.out` and `<name>.in` with `node.autoconnect=false` and share `node.link-group`; the mic chain's null source stays out of that group, or PipeWire schedules it with the streams and it hears nothing. A mic or cable chain's `outputs` are listen destinations: the playback end also feeds them, so "hear yourself" is a chip in the strip. Every destination has its own send: the playback stream carries one stereo pair per destination (FL/FR for the first, then surround positions RL/RR, SL/SR and so on, up to eight pairs; AUX positions are out because PipeWire's channel mixer folds anything past 63 onto MONO and mutes it), the callback copies the processed main pair into the other pairs with a ramped gain each, and the control plane links destination `i` from pair `i` and sends the gains with the `sends` line; a change in the number of destinations reconnects the playback stream. Slots run in order; built-ins link `claritas-core` (EQ today, Comp a passthrough until Claritas ships it); CLAP plugins are hosted with `clack-host` (`canalis_chain::clap`): the loop thread loads the bundle, reads the parameter list through the params extension, applies saved values with a flush on the inactive plugin, activates for the stream rate and `MAX_QUANTUM`, and hands only the audio processor with its preallocated port and event buffers to the callback; parameter changes cross the ring and become `ParamValueEvent`s in the next process call; a processor that comes back as garbage is stopped and deactivated on the loop thread. LV2 plugins are hosted with lilv (`canalis_chain::lv2`), which like suil is opened at run time (`canalis_chain::lilv`: libloading, the subset of lilv we use, lilv's inline instance functions redone on the descriptor) so `canalis-chain` needs only libpipewire to start; without lilv an LV2 slot reports the install hint as its error, `--scan-lv2` exits 3 with it and the snapshot carries it as `Graph::lv2_off`, and without suil LV2 slots run with no window: the world is loaded once per chain process on the first LV2 slot, the plugin is instantiated with a process-wide URID map, every port is wired at load (audio and CV ports to `MAX_QUANTUM` buffers, control ports to one `f32` each, atom ports to 16 KiB buffers reset before every run), the instance is activated and handed to the callback; a control change is one `f32` store, the latency port is read after each run into an atomic, a returned processor is deactivated on the loop thread. Mono plugins hear the mid of a stereo chain and feed both sides. An LV2 plugin's own UI (`canalis_chain::lv2ui`) goes through suil into the same X11 window a CLAP GUI would get: the X11UI type when the plugin ships one, else whatever suil can wrap; features `ui:parent`, `ui:resize`, `instance-access` and the URID map; its idle interface runs from the 30 Hz tick, control values it writes are queued, applied to the processor and reported as `params` so the control plane persists them. The catalogue of installed plugins (`session/plugins.rs`) comes from `canalis-chain --scan <bundle>` run once per `.clap` under `$CLAP_PATH`, `~/.clap`, `/usr/lib/clap` and `/usr/lib64/clap`, so a bundle that crashes on load kills a throwaway process; plus one `canalis-chain --scan-lv2` per scan that lists what lilv finds (TTL parsing only, about a second); CLAP results are cached by bundle path and mtime in `$XDG_CACHE_HOME/canalis/plugins.toml`, rescanned at start when a bundle changed and on request, and published in the snapshot for the picker. Plugin GUIs (`canalis_chain::x11`) are CLAP `gui` X11 embedded: the chain process opens one X11 connection (XWayland on Wayland) when it starts, creates a top-level window per open GUI, hands its id to the plugin with `set_parent`, pumps the socket from the loop thread (an io source plus the 30 Hz tick, since x11rb buffers events), forwards WM close and resize to the plugin, serves `request_resize`/`show`/`hide`/`closed` from the host callbacks, and reports `gui` open/closed lines; closing a slot closes its window, and a closed window is unmapped at once but destroyed 250 ms later so the plugin's own window thread finishes first. Plugin state (CLAP `state` extension) is saved by the chain 400 ms after the last change (the plugin's `mark_dirty` or a param from us), base64 in a `state` report with a refreshed `slot_info`; the control plane writes it into the slot's `spec.state` and drops the `params` map, which only carries values for plugins without state; at load the state goes in first, then any params, before activation. LV2 plugins get the same treatment through their `state:interface` (`canalis_chain::lv2state`): the chain calls the plugin's `save` on the loop thread once changes settle (a control from us or from its UI, or its UI closing, since a UI can change state through atoms the host never sees) and keeps the POD, portable properties by URI together with the control port values as one base64 blob in `spec.state`; at load a factory preset named in `spec.preset` is restored first through lilv (the `pset:Preset` resources related to the plugin are listed in the slot info with their labels), then the blob's properties through `restore` before activation, then `params`. A chain's endpoints are any nodes, other chains included (an *insert* chain): several inputs are summed by PipeWire, several outputs each get a copy, which is how parallel paths are built; the control plane refuses a pick that would close a cycle through chains' inputs and outputs. Latency of all slots is summed and reported through `SPA_PARAM_ProcessLatency`. A chain also has a key input, `<name>.key`: a third stream object from the start, connected (so present as a node) only while the config names a key node, which the control plane links into it like any input; the callback drops all but its newest buffer and hands it to every slot whose plugin has a sidechain port (CLAP inputs after the main one, LV2 audio inputs marked `lv2:isSideChain`), and the other slots never see it. A *hardware insert* slot (`SlotSpec::Hardware { send, ret, latency }`) uses the same two mechanisms the other way round: while one exists the playback end carries one more pair (positions TSL/TSR, after the send pairs) and a return input `<name>.insert.in` is connected; the control plane links the pair to the interface output device named in `send` and the device named in `ret` into the return; in the callback the slot copies what enters it into the chain's insert send buffer (copied out to the pair after the fan-out) and replaces it with the newest return buffer, so everything after the slot hears the gear one trip late, which the slot reports as its latency. A `measure` command sends a full-scale click on the send and the slot counts samples until the return rises above a quarter; the result goes up as a `measured` line, into the slot's `latency` in the config, and into the chain's published latency. A *parallel group* slot (`SlotSpec::Group { lanes }`) holds up to four lanes, each its own slot list: the callback copies the slot's input into every lane's scratch block, runs the lane's slots there, then sums the lanes back with a per-lane ramped gain, each lane first delayed by the difference between its slots' latency and the slowest lane's so the sum stays coherent; the group reports the slowest lane. Slots inside lanes keep every message's single `slot` field through a composite id, `1000 + top * 100 + lane * 10 + sub` (`SlotPath`), which the chain routes into the lane, the control plane resolves into the nested TOML tables (`slot_table_mut`) and the strip draws as nested cards. A replaced group comes back whole through the garbage ring and its lanes' plugins are retired one by one. The chain output's loudness (`canalis_chain::loudness`: BS.1770 K-weighting, 100 ms block ring for momentary and short-term, a 0.1 LU histogram with the absolute and relative gates for integrated, a 4x windowed-sinc interpolator for true peak) is computed in the callback without allocation and rides the `meters` line.
- **Soundboard (`canalis-pads`, ADR 0008).** The one real-time stream inside the service: `canalis.soundboard`, an output stream of class `Audio/Source` (two capture ports apps and chains can record, unlike the `Audio/Source/Virtual` case above), `node.always-process`, while the Pads tab is switched on. Its callback runs the `canalis-pads` engine, which mixes decoded sounds without allocating; the control-plane loop sends it commands and reads its events over rtrb queues. The reconciler owns every link leaving the node: the board's `outputs` and, when monitoring, the default output.
- **Chain process boundary.** The control plane spawns `canalis-chain --node-name --label --kind` and talks to it over the child's own pipes, one JSON object per line (`canalis_chain::ipc`): slots, bypass, mix, EQ bands, CLAP params, GUI open/close, the chain mute (a 10 ms gain ramp after the slots) and the sends (pair count and gains) go down on stdin; `up`, `format`, `meters` (30 Hz peaks), `latency` and `slot_info` (a built slot's plugin name, parameters with ranges, or the load error) come up on stdout; stdin EOF means the control plane is gone and the chain quits. Inside the process the loop thread owns the slot list and builds `SlotRunner`s (which allocate), moves them into the callback through an `rtrb` ring as `Message`s and frees what comes back through a garbage ring; band changes cross by value. A chain that dies is restarted with every slot bypassed and shown as such; a fatal signal (`canalis_chain::crash`) first writes a `crash` line naming the slot the callback was in, from a handler that uses only an atomic, a stack buffer and `write(2)`, so the strip can say which plugin took the chain down. `canalis-pw` never links `canalis-chain`: slot contents are opaque TOML there and typed only in the GUI; a live tweak is mirrored into the saved slot table by message type (`bypass`, `mix`, `eq_bands`, `param`).
- **GUI (`apps/canalis`).** Four views over the same snapshot. Plugin GUIs are floating windows opened by the chain process, never embedded.

## Persistence
`~/.config/canalis/config.toml` (`canalis_pw::Config`), `version = N` first and migrated on load (ADR 0005; an unreadable or newer file is never saved over, `Graph::config_problem` tells the window): `[[scene]]` entries hold named routing states (defaults, app targets, chain ends, mutes, slot bypasses) that `Command::ApplyScene` recalls as a diff against the current snapshot, so only what differs is touched; `[[virtual_device]]` (name, label, kind), `[[link]]` (output and input as node + port name), `[targets]` (`application.name` → `node.name`) and `[[chain]]` (name, label, kind, icon, slots as the chain's own tables, inputs and outputs by `node.name`, `gains` as destination name → dB; the order of the entries is the order of the strips), `labels` (`node.name` → the user's name), `hidden` (device node names and app names kept out of the views) and `[apps.<name>]` (an app's label and colour, applied to its streams in the snapshot). Never an id. The control plane reapplies all of it after every published snapshot: missing virtual devices and chain processes are created, chain ends are linked channel by channel to their named nodes, streams are re-targeted by app name; each request is tried three times per connection and the counter resets only on reconnect or a user action on that key, never from what the registry shows, so a flapping object cannot cause a request loop. The control plane also owns one MIDI input, `canalis.midi` (`canalis_pw::midi`): an `application/control` stream on every connection whose buffers (UMP packets, or raw MIDI bytes from older bridges) are parsed on the loop thread into `MidiEvent`s; the reconciler links the configured `midi_input` node's first output port into it and nothing else. A learn (`Command::Learn`) maps the next CC or note to a target (a chain's mute, a slot's bypass by slot id, a send gain, a scene) as a `[[control]]` entry keyed by the port it was learned on, so a mapping from an absent controller stays listed and inert; later messages fire through `ControlMap::fire`, which turns them into the same commands the GUI sends, so they work in daemon mode too. The service owns the audio (ADR 0006): `canalis --daemon` runs the control plane and its chains and serves them on `$XDG_RUNTIME_DIR/canalis/canalis.sock` (`canalis_pw::remote`, the app's shared runtime dir in a Flatpak). One JSON object per line: up go `hello` (protocol and build), the whole `graph` after every snapshot and `meters` for every chain at 30 Hz (`MeterValues`; the client keeps its own `ChainMeters` per chain name and hands them out in the graphs, so views read meters as before), and `bye` when the service stops on purpose; down go `command` (any `Command` but `Quit`, which is dropped) and `shutdown`. Windows say `window` after `hello`; `raise` and `close` from any client go to them as `raise`/`close`, and the asker gets `windows` (whether there was one): a launch raises the open window and exits, the tray icon's click closes it or opens one. `hello`, `shutdown` and `bye` never change shape. The window, the tray and `canalis scene`/`canalis quit` are clients. The tray (`apps/canalis/src/tray.rs`, `ksni` on async-io, no tokio) runs on a thread of the service and talks to it through the same socket; its icon is `assets/canalis-icon.svg`; Quit sets the service's stop flag, so windows get `bye`; a window starts a service when none answers (systemd first, through a unit rewritten whenever it names another binary or `flatpak run`, else a `setsid` child) and never stops it, restarts a service of another build once, and closes on `bye`. The service is the only writer of `config.toml`; `CANALIS_CONFIG` gives a window its own in-process control plane for tests and screenshots.

## Real-time rules
Inside the chain callback: no allocation, locks, syscalls, logging or panics; debug builds abort on an allocation through `assert_no_alloc`'s global allocator. Buffers for `MAX_QUANTUM` (8192) are allocated when a runner is built; quantum changes at runtime are handled by slicing, never by reallocating. Parameter changes arrive through the `rtrb` ring; meters leave through atomics.

## Dependency direction
`apps/canalis → canalis-pw`, `apps/canalis → canalis-chain` (shared types only). The Claritas EQ and Comp are not a dependency but CLAP plugins Canalis ships in `<bin>/../lib/clap` (ADR 0007); `canalis_pw::claritas` knows Claritas EQ's parameters, for config migration 1 → 2. `canalis-pw` and `canalis-chain` never depend on each other.
